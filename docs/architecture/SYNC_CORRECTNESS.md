# sanIP 同步正确性约束

> 最后更新：2026-07-29
>
> 适用范围：sanOmni 桌面端与 `sanomni-sync-server` 的 `sanIP` 协议域

本文档记录双向同步必须长期保持的正确性约束。实现可以重构，但不能在没有数据迁移、兼容方案和回归测试的情况下破坏这些不变量。

## 1. 状态含义

- 客户端 `sync_changelog`：本机尚未成功 Push 的业务变更。
- 服务端 `sync_log.version`：服务端按 `sanIP` 域分配的单调递增变更版本。
- 客户端 `last_sync_version`：本机最后一次**成功提交 Pull** 后已经消费到的服务端版本。
- 客户端 `sync_pending_downloads`：数据库记录已应用、但文件尚未通过下载和哈希验证的可重试任务。

`last_sync_version` 不是“服务端当前最新版本”，也不是“本机最后一次 Push 得到的版本”。

## 2. 游标不变量

1. Push 成功只证明服务端接收了本机变更，不能证明本机已消费此前的远端变更。
2. 同一轮同步即使先 Push，后续 Pull 仍必须从进入本轮时的 `last_sync_version` 开始。
3. 只有远端数据库变更全部应用且本地事务成功提交后，才能把游标推进到响应的 `latest_version`。
4. 请求失败、解析失败、未知表、写入失败、应用数量不一致或提交失败时，游标必须保持不变。
5. 增量 Pull 返回 0 条变更时，客户端必须用服务端快照检查远端记录是否仍有本机缺失项。发现缺口说明游标与本地真实状态不一致，必须通过保留的完整服务端历史走同一事务化 Pull 路径恢复；不能因为游标已等于 `latest_version` 就宣布同步完成。

## 3. 数据库事务不变量

### 客户端 Pull

- 一次 Pull 响应中的数据库变更必须在同一事务中应用。
- 每条变更必须被明确识别并成功执行；不能用“尽量应用”后提交的方式跳过失败记录。
- 临时停用同步触发器和恢复触发器属于同一事务边界。失败回滚后，原有触发器状态不能丢失。

### 服务端 Push

- 业务表写入、`sync_log` 写入和写入后验证必须位于同一事务。
- 任一变更被拒绝时，不得留下只有日志没有业务数据，或只有业务数据没有日志的半完成状态。
- 更新被外键引用的父表时必须使用 `INSERT ... ON CONFLICT DO UPDATE` 或等价的原位更新，禁止使用 SQLite `INSERT OR REPLACE`。`REPLACE` 会删除旧父行，可能触发 `ON DELETE CASCADE` 清除子记录。

## 4. 记录身份不变量

- 有稳定 UUID 的表直接使用 UUID 作为 `record_id`。
- 复合记录优先从 `data_json` 的结构化字段取得业务键；分隔字符串只能作为旧协议兼容回退，不能假设业务 ID 不含下划线等字符。
- `ip_creations` 的跨设备身份为 `ip_id|文件名`。文件名提取必须同时识别 Windows `\` 与 Unix `/` 路径分隔符，不能把设备绝对路径作为远端身份。
- 同一 IP 下相同文件名当前被定义为同一逻辑创作图片。若未来需要允许重名文件，必须引入稳定 UUID 并设计协议迁移，不能直接修改拼接规则。
- 复合主键发生变化时，使用旧身份 `DELETE` 加新身份 `INSERT`，不能只发送无法定位旧行的 `UPDATE`。

## 5. 表覆盖不变量

任何加入 `sanIP` 同步域的可变表，必须同时具备：

1. 本地 INSERT、UPDATE、DELETE 变更捕获；
2. Push 文件哈希收集与上传（如果包含文件）；
3. 服务端域白名单、写入、删除、验证和快照支持；
4. 客户端 Pull 写入、删除、路径重写和文件下载（如果包含文件）；
5. 强制全量重推支持；
6. 插入、更新、删除和跨设备身份的回归测试。

2026-07-29 已补齐此前遗漏的 `ip_character_sheets`、`ip_creations` 和 `ip_relations`。

## 6. 文件一致性不变量

- Push 前读取本地文件失败、远端缺失检查失败、上传失败或服务端返回哈希不一致时，本轮 Push 必须失败；不能清理对应的本地待推送日志。
- 下载后的文件必须重新读取并计算 SHA-256；只有哈希与服务端声明一致才算文件落盘成功。
- 下载、读回或哈希验证失败必须进入 `sync_pending_downloads`，并在后续同步中重试；不能只打印日志后遗忘。
- 数据库变更采用事务原子性，文件传输采用可重试的最终一致性。因此“数据库 Pull 成功”不等于“全部文件已经落盘”，界面和诊断信息需要保留这个区别。

## 7. 恢复操作边界

“强制全量重推”只是把本机现有记录重新加入 Push 队列：

- 它不会判断哪台设备的数据更新；
- 它不会自动合并同 ID 冲突；
- 它不会自动删除服务端独有记录；
- CAS 只能避免相同文件重复存储，不能保证元数据合并正确。

执行前必须备份服务端与本地数据库，并确认本机是数据最完整的来源。历史缺失需要先通过快照、备份或逐表对账确认，不能把重推当作无风险修复按钮。

客户端的自动缺口恢复只补回服务端快照存在、但本机缺失的记录；它不会根据快照自动删除本机独有记录。恢复会从服务端 `sync_log` 保留的完整历史中筛选每条缺失记录的最新有效变更，并按父表到子表的依赖顺序应用，以保留文件哈希并复用下载、哈希校验、事务回滚和失败重试逻辑。若完整历史已被裁剪且无法覆盖快照缺口，客户端必须失败并保持游标不变，不能提交不完整恢复。

## 8. 发布与验证清单

- [ ] 先升级服务端，再升级所有参与同步的客户端。
- [ ] 服务端父表更新不会删除现有子记录。
- [ ] Push 后 Pull 仍从上一次成功 Pull 游标开始。
- [ ] 增量 Pull 为空但快照存在本机缺失记录时，会自动从完整历史补回并报告数量。
- [ ] 任一数据库变更失败时整批回滚且游标不变。
- [ ] Windows 与 Linux 路径对同一创作图片产生相同身份。
- [ ] 每张含文件的业务表都覆盖上传、下载、哈希校验和重试。
- [ ] 新增同步表同时覆盖触发器、服务端、Pull、快照和强制重推。
- [ ] 在数据库副本上执行多设备插入、更新、删除和断网重试测试。
- [ ] 强制全量重推前已完成备份和数据源确认。
